# SubMerge 前端风格规范

> 适用范围：`fronted/`。本规范以当前已实现的 React 界面为准；新增或修改页面时应优先复用现有模式，不因统一样式做无关重构。

## 产品与界面目标

SubMerge 用于管理订阅源、策略组、分流规则和发布记录。界面应帮助管理员快速完成三件事：看清当前配置和状态、定位失败项、执行下一步操作。

可见文案使用简洁、明确的中文，例如“发布配置”“加载失败”“重试”。操作、状态和影响要说清楚；避免无关的宣传语、抽象比喻和模板化设计口号。

## 当前视觉基础

- 使用 React、Tailwind CSS v4、Radix/shadcn 风格组件和 Lucide 图标。
- 浅色与深色主题均已支持；`src/index.css` 是颜色、字体、圆角和主题变量的唯一入口。
- 整体是蓝灰色系：`primary` 用于主要操作、链接、焦点和当前导航项；`muted`、`secondary` 用于次级背景和低优先级操作；`destructive` 只用于删除与错误。
- 全局字体为系统无衬线字体；版本、数量、IP、规则和 URL 等需要对齐或精确识别的内容可使用 `font-mono` 或 `tabular-nums`。
- 常规内容以白色/深色卡片、细边框、适度圆角组成；卡片与表格用于组织信息，不应为了装饰而重复嵌套。
- 图表使用 `--chart-*` 变量；业务页面不能新增硬编码颜色。登录页右侧视觉区域是现有的入口页例外，不可直接复制到控制台页面。

新增样式优先使用 `bg-background`、`bg-card`、`text-foreground`、`text-muted-foreground`、`border-border`、`bg-primary`、`text-destructive` 等语义类。需要新增全局视觉变量时，先在 `src/index.css` 定义浅色和深色值。

## 页面结构

登录后的页面由 `AppShell` 统一提供：左侧可折叠导航、顶部工具栏和内容区。页面不应自行新增第二套侧栏或固定顶栏。

- 内容区最大宽度为 `100rem`，常规页面使用 `px-4 py-5`，大屏使用 `lg:px-6 lg:py-6`。
- 每个页面通过 `PageHeader` 提供一个 `h1`、说明文字和页面级操作；操作区会在窄屏换行。
- 主要数据区使用 `DataPanel` 或 `Card`。列表和表格保留容器的横向滚动，不压缩列到不可读。
- 当前导航项使用 Sidebar 内置的 active 状态；主题切换和应用更新入口位于顶部工具栏。
- 移动端导航自动切换为抽屉，页面布局应能在窄屏单列展示。

登录页是独立入口：桌面端为表单和说明图的双栏布局，窄屏只显示表单。不要把登录页的深蓝背景、说明图或绝对定位标签带入后台业务页面。

## 组件使用

| 场景 | 使用组件 | 规则 |
| --- | --- | --- |
| 页面标题与主操作 | `PageHeader` | 一页一个标题；主操作放入 `actions`。 |
| 列表、表格和筛选结果 | `DataPanel` + `Table` | 面板标题说明对象或范围；表格保持横向滚动。 |
| 概览指标和独立信息块 | `Card` | 用于有明确边界的信息组；不要把每一行信息都单独做成卡片。 |
| 加载、错误、空列表 | `ResourceState` | 统一显示加载、错误、重试与空状态，不重复实现。 |
| 创建和编辑 | `FormDialog` | 标题、说明、字段和取消/提交按钮使用统一结构。 |
| 删除、发布、回滚等高风险操作 | `ConfirmAction` | 明确说明影响，必须二次确认。 |
| 即时反馈 | `toast`（Sonner） | 使用中文短句；全局显示在顶部居中。 |

通用控件从 `src/components/ui/` 引入：`Button`、`Input`、`Select`、`Textarea`、`Badge`、`Alert`、`Dialog`、`Table` 等。业务页面不应另造样式相近的原生控件。

## 交互与状态

- `Button` 的 `default` 用于主要提交或跳转，`outline` 用于次级操作，`ghost` 用于表格行和工具栏，`destructive` 用于删除或不可逆操作。一个页面头通常只有一个主按钮。
- 按钮、输入框和可点击卡片必须保留组件已有的 hover、focus-visible、disabled 和 loading 状态；纯图标按钮必须提供中文 `aria-label`。
- 表单使用 `Label` 和字段错误文字。校验错误不能只改变边框颜色。
- 成功、警告、失败和待处理状态必须同时提供文字；颜色只是辅助信息。`Badge` 用于短状态，`Alert` 用于需要用户理解并处理的异常。
- 请求进行中保留加载指示，失败时提供可用的重试入口。不要用页面跳动、自动刷新或装饰性动画代替状态反馈。
- 页面内动效保持短且克制，优先使用 `opacity`、`transform` 或 `color`；新增非必要动效应考虑 `prefers-reduced-motion`。

## 内容与数据呈现

- 订阅 URL、Token、密钥、规则和 IP 需考虑截断、复制或展开，不让长字符串撑破布局。
- 数量、版本、访问次数和时间使用一致格式；表格中的数值根据语义右对齐，状态和名称保持易扫读。
- 空状态说明“当前没有什么”和“用户下一步可以做什么”；错误状态保留服务端错误信息并提供重试或返回路径。
- 用户可见错误、提示和按钮使用中文，避免直接展示英文内部错误码；必要的技术详情可放在 `title`、日志或展开区域。

## 实现边界

样式和行为按以下顺序落点：

1. 主题变量、全局基础样式：`src/index.css`。
2. 可复用的基础控件：`src/components/ui/`。
3. 跨页面布局和状态组件：`src/components/`。
4. 仅属于某个业务功能的布局：对应的 `src/pages/` 或 `src/features/`。

不在业务页面硬编码品牌色、阴影、圆角或 z-index。确有需求时先扩展语义 token 或共享组件。不要在未涉及的页面中批量替换组件、清理样式或改变布局。

## 提交前检查

- [ ] 页面是否使用了 `AppShell`、`PageHeader` 和已有共享组件？
- [ ] 浅色、深色、窄屏和长中文文本下是否仍可读、可操作？
- [ ] 是否为加载、空数据、失败和高风险操作提供了正确反馈？
- [ ] 是否使用语义颜色和现有控件，而非新增硬编码视觉常量？
- [ ] 交互控件是否可键盘访问，图标按钮是否有 `aria-label`？
- [ ] 是否运行 `cd fronted && npm run typecheck`；涉及交互时是否运行相关 `npm test`？
